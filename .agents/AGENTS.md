# Project Customization Rules for TRIBE: NEON REIGN

This file defines the project-specific rules, design constraints, and technical specifications that all agent instances must follow when working on this codebase.

---

## 1. 得意スキルボーナス（AP軽減シナジー）の仕様
- **仕様詳細**:
  - キャラクターが装備しているスキルが得意スキル（ownerIdとキャラクターIDが一致）である場合、自動スキル発動時の**消費APが -1 軽減**されます（※最低消費APは1）。
  - **威力（ダメージ・回復量）の上昇補正や、デバフの持続ターン延長は適用されません。** 等倍（記載スペックのまま）で発動します。
- **実装箇所**:
  - `src/hooks/useBattle.ts` 内のオートスキルAI（手番キャラクターが装備スキルを使用する際のAP消費計算）。
  - `src/app/components/CardBattleView.tsx` 内の `SETUP` (出撃準備画面) でのカード詳細ポップアップ。

## 2. 装備品ステータスのレベル・限界突破スケーリング
- **パラメータ算出式**:
  - レベル（`Level`）および限界突破（`plus_val`）が進行した際の装備ステータス計算式：
    - `ATK / DEF / HP / SPD / LUK` = `Math.floor(ベース値 * (1 + (Level - 1) * 0.05 + plus_val * 0.10))`
    - ※対人戦バランスの最適化に伴い、SPD/LUKについても一律でスケーリングが適用されます。
- **実装箇所**:
  - `src/utils/stats_calculator.ts` の `getCharacterTotalStats` による計算処理。
  - `src/app/components/CharacterTab.tsx` の装備詳細パネル。

## 2.1 キャラクターの成長パターン・覚醒マスタによるスケーリング
- **仕様詳細**:
  - キャラクターのレベルアップ時のステータス成長（HP/ATK/DEF/SPD/LUK）は、キャラクターごとに割り当てられた成長パターンマスタ（`character_growth_patterns` / `CHARACTER_GROWTH_PATTERNS` 定数）の `hp_gain / atk_gain / def_gain / spd_gain / luk_gain` に基づいて動的に線形加算されます。
  - 覚醒時のステータスボーナス（HP/ATK/DEF/SPD/LUK）および消費キャッシュ額は、覚醒マスタ（`character_awakening_master` / `CHARACTER_AWAKENING_MASTER` 定数）の `hp_bonus / atk_bonus / def_bonus / spd_bonus / luk_bonus` および `required_cash` に基づいて算出・消費されます。
- **実装箇所**:
  - `src/utils/stats_calculator.ts` の `getCharacterBaseStats` 関数。
  - `src/app/context/GameContext.tsx` の `handleCharacterAwaken` 内のキャッシュコスト消費判定。

## 3. 世界観・ビジュアルコンセプト (Matte Outlaw Circular UI)
- **コンセプト (Matte Outlaw Circular UI)**:
  - 画面を四角いグリッド枠等で細かく分断せず、背景の夜の街のグラフィックが画面全体に広がり、その上に直接UI要素が浮き出る「シームレスな全画面一体キャンバス構造」を徹底する。
  - 「無骨すぎるサバイバル・ミリタリー」に偏るのを禁止し、現代のストリートファッションアパレルに見られるような「マット加工（つや消しスチール、つや消し樹脂）」の洗練された硬質な質感を基本とする。
  - 「拠点」という用語・概念は完全に禁止する。常に「拠点」または「マイページ背景（ビジュアルエリア）」と呼称・記載すること。
- **丸型漢字グラデーションボタンの配置**:
  - メニューボタンは、つや消しシルバーの金属ベゼルで縁取られた「赤（連合）」「青（喧嘩）」「緑（制圧）」などの丸型カラーボタンに統一する。
  - ボタン中央には極太の白フォントで大きな「漢字」で機能名を描画し、HTMLのテキスト重ねは排除する。
- **世界観バインド（未来SF/サイバーパンク表現の徹底排除）**:
  - 本作は「未来SF」「サイバーパンク」「ハイテク電脳」「サイボーグ」ではありません。現代に存在するリアルな「ストリート・アウトロー（現代裏社会 of 泥臭さ・ミリタリー・ナイロン製ストリートギア）」が主役です。
  - 提案書、コード内コメント、設計書、説明文において「サイバー」「サイバーパンク」「SF」「未来ハイテク」「電脳」「ホログラム」といったジャンルの言葉や形容表現は**一切使用禁止**とします。
  - UIパーツが自ら光を放つホログラムのようなSF的UI表現を廃止します。ネオンカラーはUIを光らせるためではなく、新宿や渋谷の夜のネオン看板の光が金属エッジ部分にぼんやりと鈍く反射する環境ライティング（Subtle Environment Reflections）としてのみ使用します。
- **保留ルール**:
  - まだゲーム上の立ち絵アセット（`user_characters`）が定義されていないキャラクター（レオン、ユウキ、カイト、コハル、サクラなど）の専用武器・専用装備は、**画像アセットの生成をスキップし、モックUI上の表示枠のみ定義する**。

## 4. UI/UX実装・スタイリングの制約
- **Vanilla CSSの徹底**:
  - インラインスタイルや Tailwind 等のad-hocなユーティリティクラスの混用を避け、`src/app/globals.css` に定義された共通変数およびクラスを使用する。
- **ローディング表現**:
  - 非同期処理待ちのローディング表示は、シンプルなスピナーのみ（回転円環のグラフィックなど）を表示する。
  - `Now Loading...` や `読み込み中...` といったローカル文字ラベルの併記・表示は一切禁止。
- **即時レスポンス（押し込み効果）**:
  - ボタン要素には `transform: scale(0.95)` や `active-scale-effect` などのタップ時の押し込みリアクションを必ず付与する。
- **絵文字（Emoji）使用の禁止**:
  - UIのアイコンやラベルに絵文字（📍⚡◆🎁等）を使用することを禁止する。
  - 代わりにSVGアイコン、またはテキストラベル（例: 「拠点」「Cash」「Dia」「AP」）で代替する。
- **スクロールバーのスタイル統一**:
  - スクロールバーにネオンカラー（シアン・マゼンタのグラデーション等）を使用することを禁止する。
  - つや消しメタル調のグレー系（例: `rgba(160, 160, 170, 0.3)`）で統一する。

## 5. アプリケーション設計と構造ルール
- **Context ＆ カスタムフックへのロジック移譲**:
  - 状態定義および Supabase DB との状態同期は React Context (`GameContext.tsx`) にて一元管理し、バトル進行などの巨大なドメインロジックは専用カスタムフック (`useBattle.ts`) へ切り出してカプセル化します。
- **コンポーネント指向CSSの配置ルール**:
  - UIコンポーネントは `src/app/components/` に配置し、対応する CSS ファイルは、コンポーネントと**同一ディレクトリに同名で配置**してコンポーネント内から直接インポートします。

## 6. ユーザー招待・ギフトコード機能の仕様
- **仕様詳細**:
  - ギフトコードを発行・確認できるのは `users.gift_code` カラムおよび `user_invitations` テーブルを使用します。
  - 新規プレイヤーは組織設立時（セットアップ画面）に任意のギフトコードを入力して開始できます。自分自身のコードは使用できません。
  - 同一のギフトコードは最大10人まで使用可能です。11人目以降が入力しようとすると「このギフトコードは10人使用済です」というエラーメッセージを出して設立を制限します。
  - 招待が成功した際、招待した側はミッションマスタ（トリガー: `USER_INVITE`、ミッションID `m_invite_01`〜`m_invite_10`）を通じて1名ずつ報酬を回収できます。また、招待された側（入力した側）にはプレゼントBOX経由で入力報酬（ダイヤ+100）が即時付与されます。
  - プロフィール設定画面には「ギフトコードを発行」ボタンを配置し、タップ時にポップアップでコード表示、コピー機能、およびLINEで招待するボタン（LINEブランドカラー `#06C755` 準拠のメッセージ送付リンク）を提供します。

## 7. マイページ画面（HomeTab）レイアウト ＆ メニューボタン仕様

### ヘッダー（Header.tsx / Header.css）
- **2行構成のモバイルヘッダー**:
  - **Row1**: ユーザー名、所属ギルド名（未所属時は「未所属」バッジ）、レイドアラート（開催時のみ）、総合力
  - **Row2**: Lv.バッジ + 各ステータスの個別枠ボックス（`Cash` / `Dia` / `AP`）
  - 各ステータス枠は `border: 1px solid rgba(255,255,255,0.08)` のボックスで区切り、ラベルテキスト（7px, グレー）＋値テキストで構成する。
- **装飾**:
  - ヘッダー上部に `margin-top: 8px` のスペースを確保する。
  - 上下に金のグラデーションライン（`border-image`）を配置する。
  - CSSグラデーション背景のみで構成し、背景画像は使用しない。

### ビジュアルエリア（お気に入りリーダーキャラクター ＆ 拠点背景表示）
- **アバターシステムの一時オミット**:
  - 現在アバター主役化は一時オミット中です。ビジュアルエリア中央にはお気に入りリーダーキャラクター（NPC立ち絵）が表示されます。
  - アバター背景ではなく、滞在中の拠点（新宿など）ごとに連動した背景画像（`bgUrl`）がビジュアルエリア背景として表示されます。
  - ※ただし、現在地の表示や「拠点移動」機能はビジュアルエリア上部のオーバーレイHUD（`.mypage-base-overlay`）として維持します。
- **拠点情報オーバーレイ（`.mypage-base-overlay`）**:
  - ビジュアルエリア**内部**の最上部に `position: absolute` で配置する。
  - 背景は上から下への透過ダークグラデーション（`rgba(0,0,0,0.75)` → `transparent`）。
  - テキストラベル「拠点」+ 拠点名 + 「｜」+ 「支配: ギルド名」を1行に集約。
  - 右端に「拠点移動」ボタンを配置。
- **サイドアイコン（左右分散・ラベル付き）**:
  - 左側: ミッション、プレゼント（ゲームプレイ系）
  - 右側: お知らせ、設定（情報・設定系）
  - 拠点オーバーレイの下（`top: 42px`）に配置する。
  - 各アイコンはインラインSVG + テキストラベル。バッジカウント表示あり。
- **ビジュアルエリアのCSS**:
  - `height: 50vh; overflow: hidden;` で固定。内部要素は `position: absolute` で配置。

### 組織設立（ゲーム開始セットアップ）画面仕様
- 新規プレイヤーは組織設立時（SetupView）に、ユーザー名、初期配備メンバー、初期滞在拠点を選択してゲームを開始します（アバターメイキングUIは一時オミットされています）。

### 丸型漢字メニューボタン（連合 / 喧嘩 / 制圧）
- ビジュアルエリアの**外側**（兄弟要素）に配置し、`margin-top: -48px` のネガティブマージンでビジュアルエリアに重ねる。
- `position: relative; z-index: 15;` で前面に表示。
- 中央の喧嘩ボタンを最大サイズ（`96px`）、左右は `80px`。
- ボタン画像は `public/menu/menu_allies.png`, `menu_fight.png`, `menu_conquest.png`（画像内に漢字描画済み）。
- HTML上のテキスト重ねは排除する。

### チャットウィジェット
- 丸ボタンの直下に配置（間に不要なスペースを入れない）。
- チャットログは `height: 108px; min-height: 108px; max-height: 108px;` で常に6行分の固定サイズを確保し、サイズを可変させない。
- ヘッダー部クリックで開閉可能（閉じ時はヘッダー1行のみ表示）。
- スクロールバーはつや消しメタル調グレー（ネオンカラー禁止）。

### フッター
- `マイページ`, `ガチャ`, `ギルド`, `キャラクター`, `メニュー` の5項目。
- SVGアイコン + テキストラベル構成。
- 「メニュー」タップで各機能へのリンク一覧画面（MenuTab）に遷移する。

### UIアセット生成と透過処理 (Chroma key / Jimp)
- ゲームUI用ボタンやバッジなどを画像生成する際は、`solid chroma key green background`（緑背景）で生成し、Node.jsスクリプト（`scratch/chromakey.js` ➔ `Jimp` ライブラリのピクセル走査）を用いて自動的に周囲の緑を透過処理（アルファ値0）した透過PNGに加工して `public/` へ配置します。

## 8. 正式名称の統一 ＆ AIによる勝手なテキスト補完・創作の禁止
- **「プレイヤー名」の完全禁止と「プレイヤー名」への統一 (厳守)**:
  - 提案書、コード内コメント、ドキュメント、UI上のすべてのラベルにおいて「プレイヤー名（および組織）」という表現・表示は**一切使用禁止**とします。
  - すべて**「プレイヤー名」**に統一してください（例: HUDの `拠点名 ｜ 支配: プレイヤー名` は、正しくは `拠点名 ｜ 支配: プレイヤー名` とします）。
- **機能・画面名の正式名称マッピング**:
  - UIに表示する各画面・機能・ボタンのラベル文言は、モバイル版およびマスターデータで定義された「以下の日本語の正式名称」のみを使用し、英語表記（SHINOGI, ARENA, WAR 等）や、勝手に創作したサブタイトル・副題を併記してはなりません。
    - 〇 正式名称: `クエスト` （× シノギ, 遠征, SHINOGI, 派遣シノギ）
    - 〇 正式名称: `PvP` （× 闘技場, ARENA, 単独アリーナ）
    - 〇 正式名称: `GvG` （× 縄張り抗争, TERRITORY WAR）
    - 〇 正式名称: `レイド` （× 強敵襲来, BOSS ALERT, RAID）
    - 〇 正式名称: `ガチャ` （× 闇ガチャ, BLACK GACHA, 取引）
    - 〇 正式名称: `キャラクター` （× 構成員, CHARACTER, 構成員育成・編成）
    - 〇 正式名称: `ショップ` （× 闇ショップ, BLACK SHOP, 闇ショップ（取引所））
    - 〇 正式名称: `マップ` （× 東京マップ, MAP）
    - 〇 正式名称: `ランキング` （× 順位表, RANKING）
- **情報の勝手な創作（補完）の完全禁止**:
  - AIの自己判断で、賑やかし用の英語サブタイトル、英語バッジ（AUTO, ARENA, WAR 等）、勝手な説明文（例：「構成員を派遣し、自動でみかじめ料を回収します」等）をでっち上げて追加してはなりません。
  - テキストや情報が不足していると感じた場合でも、勝手に追加（創作）はせず、モバイルで定義されている最小限の表示にとどめるか、または実機で必要な情報をユーザーに直接確認・質問してください。

## 9. 憶測による解決報告の完全宣言の絶対禁止
- **仕様詳細**:
  - レイアウト崩れや表示バグの修正において、コードの変更やビルドの成功のみをもって、「100%解決」「完全解決」と断定・宣言することを一切禁止する。
  - AI自身は画面を目視できないため、修正結果は常に「仮説およびコード修正の完了」として報告し、ユーザーの実機やブラウザでの確認フィードバックを真摯に待つこと。
  - また、ユーザーの開いている画面とAIが編集している開発環境が一致しているかを客観的に検証するため、不具合発生時は画面上に検証用の目印テキスト（デバッグ文言等）を一時的に埋め込んで動作確認を依頼するなどの手順を踏むこと。

## 10. 新規ランキング機能 ＆ 画面仕様規約
- **ランキングのカテゴリ**:
  - `総合力`、`ギルド総合力`、`PvP`、`GvG`、`レイド` の5つに限定する（オミットされた「成長ランキング」は絶対に追加しないこと）。
- **遷移導線**:
  - `HomeTab` の左側サブメニュー（ミッション・プレゼントの横）に、透過SVGの「ランキング」小アイコンを配置し、ワンタップでアクセスできる導線を提供する。
  - `MenuTab` の一覧に「ランキング」ボタン（シルバーカラーベース）を配置する。
- **総合力の更新**:
  - `syncUserPower` 経由で、パーティデッキ5名のステータス（HP, ATK, DEF, SPD, LUK）の合算値を `user_power_rankings` へ upsert 同期する。
- **UI/UX スタイリング**:
  - つや消しメタル調、夜のネオン看板の環境ライティング反射（Matte Outlaw UI）を徹底する。
  - 順位 badge には1位（ゴールド）、2位（シルバー）、3位（ブロンズ）のグラデーション反射を適用する.
  - スクロールバーはつや消しメタル調グレー（`rgba(160, 160, 170, 0.3)`）で統一する。

## 11. 言語およびコミュニケーションの規則
- **日本語でのやり取りの徹底**:

## 12. スレッド式BBS（掲示板） ＆ コミュニケーション機能設計規約
- **コミュニケーションの棲み分け**:
  - チャットは「全体 (GLOBAL)」「ギルド (GUILD)」のみ（エリア別・雑談は廃止）。
  - BBSは「ギルドメンバー募集 (RECRUIT)」「攻略＆雑談 (STRATEGY_CHAT)」の2カテゴリ。
- **リアルタイム同期**:
  - BBSスレッド一覧およびスレッド詳細（レス一覧）では、他プレイヤーの投稿が即時に画面に反映されるよう、Supabase Realtime等の双方向リアルタイム通信を実装する。
- **スレッドフロート仕様**:
  - スレッド一覧は、新しい返信（レス）がついた順（`updated_at` の降順）でソートして表示する。レスポンス追加時にスレッドの `updated_at` を `NOW()` に引き上げるトリガーを設定する。
- **文字数制限**:
  - チャット: 最大140文字、クールダウン（全体10秒／ギルド3秒）。
  - BBSタイトル: 最大50文字。スレッド・レス本文: 最大200文字。
- **投稿者アイコン表示**:
  - チャット・BBSともに、プレイヤーがお気に入り（リーダー）に設定しているNPCキャラクターのイラストアイコンを表示する。

## 13. レイド機能 ＆ 仕様設計規約
- **正式名称の厳守**:
  - 画面タイトルやテキスト等、UIのあらゆる場所で「強敵襲来」や「RAID」といった表記を避け、日本語の正式名称「`レイド`」に統一する。
- **ボスのエネミーマスタ設計**:
  - ボスのステータス、レベル、スキル配列等は `raid_boss_master` テーブルでマスタ定義し、戦闘構築時に動的に取得マッピングする（コード内ハードコードの禁止）。
- **出現地ランダム配置**:

## 16. ハードコードの原則禁止とDB駆動（マスタ定義）優先規約
- **基本原則**: プログラム内にゲームパラメータ（威力、効果、消費コスト、上限値、上昇倍率など）を定数やリテラルで直接記述（ハードコード）することを原則禁止とします。
- **DB駆動（マスタ定義）優先**: すべてのゲームバランス調整用パラメータ、スケーリング倍率、育成に必要なコストなどは、マスタデータテーブル（例: `skill_limit_break_master` など）で定義し、実行時に動的に参照・適用しなければなりません。
- **目的**: プログラムの修正なしでデータベースのレコード更新のみでパラメータ調整やバランスチューニングが可能な柔軟性を常に維持するため。

  - `public/se/` ディレクトリ配下に配置し、スキルの `rarity` / `effect_type` / `se_id` に応じて動的に再生制御します。
- **装備品バフの開幕一括演出 ＆ スキル演出衝突回避**:
  - 装備品やパッシブアビリティによるバフ・シールド展開は、**戦闘開始イントロ（`launchBattlePlaying`）時に一括でまとめて表現**し、バトル進行中には個別の発動演出を一切割り込ませません。スキル演出との衝突を100%回避し、テンポを維持します。
- **5桁〜6桁大桁ダメージのスケーリング ＆ 動的ダメージ計算規約**:
  - **割合防御減算モデルの採用**: 5〜6桁の大桁ダメージインフレ時にも防御（DEF）による完封（1ダメ化）や即死を防ぐため、割合防御減算式を採用します。
    \[ \text{基礎火力} = \text{ATK} \times \left(1 + \frac{\text{power}}{100}\right), \quad \text{カット率} = \frac{\text{DEF}}{\text{DEF} + 2000}, \quad \text{基本ダメージ} = \text{基礎火力} \times (1 - \text{カット率}) \]
  - **単調さを防ぐ動的補正メカニクス**: 毎回の計算が固定値になって単調化するのを防ぐため、最終ダメージに以下の動的要素を乗算します。
    \[ \text{最終ダメージ} = \text{基本ダメージ} \times \text{属性相性補正 (有利+20\% / 不利-15\%)} \times \text{乱数 (0.95〜1.05)} \times \text{クリティカル倍率 (発動時1.5〜2.0倍)} \]
  - **3桁カンマ表記 ＆ ポップアップ可変サイズ**: 数値ポップアップは3桁区切りカンマ表記とし、桁数に応じて文字サイズを自動スケーリング（CSS `clamp()`）します。

- **モバイルファースト ＆ PC縦長モバイルコンテナ適合規約**:
  - アプリ全体および戦闘画面はモバイル縦長アスペクト比（`max-width: 480px` 基準）をコンテナとして構築します。
  - PC表示時も画面中央に縦長表示され、暗転シート・カットイン・ターゲットライン・ダメージ数値ポップアップ等のすべての演出レイヤーは**PC画面全体ではなく「縦長モバイルコンテナ」の座標系を基準として完全に内部へ収容・描画**し、位置ズレや崩れを100%防止します。
- **サーバー厳格検証 ＆ チート防止セキュリティ規約 (Anti-Cheat Security)**:
  - **クライアント直接書き換えの完全無効化**: 勝敗結果、報酬獲得、所持キャッシュ/ダイヤの増減、ガチャ抽選は、クライアントからの直接UPDATEを厳禁とし、すべて Supabase の RPC (Stored Procedure) および Strict RLS ポリシー経由でサーバーサイド権限検証を行います。
  - **バトルセッション異常値リジェクト**: 開始時に発行される `battle_sessions` と連携し、ターン経過時間・ステータス上限値・ダメージ理論値をサーバー側でチェック。異常な短時間撃破や非現実的なダメージ改変を自動検出・リジェクトします。

## 21. 戦闘演出 ＆ SEゼロレイテンシ（事前プリロード・GPU合成）設計規約
- **出撃前アセット事前一括ロード (Asset Preloading)**:
  - バトル準備画面（`SETUP`）および開始処理（`launchBattlePlaying`）時に、出撃5名および敵部隊のスキルで使用される全画像アセット（カットイン画像、特殊エフェクトPNG、背景暗転素材）を `new Image()` 非同期事前ロードでメモリ上に確保し、戦闘中のHTTP遅延を完全排除します。
- **Web Audio API 先行デコード (Zero-Latency Audio)**:
  - HTML5 `<audio>` タグによる都度取得・発音遅延を回避するため、`AudioContext` を用いて全SE（.mp3）を `AudioBuffer` としてメモリ常駐させ、0.001秒単位の即時発熱再生を実現します。
- **GPU合成アクセラレーション ＆ 固定DOM運用**:
  - アニメーションプロパティには `left/top` 変更を厳禁とし、GPUアクセラレーションが機能する `transform: translate3d(...)` および `opacity` のみを使用します。
  - スキル発動毎のDOM動的生成・破棄によるガベージコレクション負荷を避け、カットイン/エフェクト用レイヤーは常駐DOMノードとしてClass切り替えで運用します。
- **倍速時の動的スケーリング**:
  - バトル速度設定（1倍速 / 2倍速）に応じて CSS カスタムプロパティ（`--speed-multiplier`）および遅延タイマーを動的乗算し、2倍速設定時にも演出表示時間をスピーディーに短縮してテンポを一切損なわない仕様とします。

## 22. 装備・スキルの一括操作、売却およびチート・ロード時間対策規約

### ① ロード時間短縮（通信バルク化）
*   所持装備・スキル数が増大するゲームデザインにおいて、1スロットずつ個別に Supabase API で更新を行うと、全身装着時（装備7スロット、スキル6スロット）に膨大な通信オーバーヘッドが発生し、ロード時間の遅延およびネットワークエラーの原因になります。
*   これを防止するため、一括解除および一括装備は必ず Supabase のストアドファンクション（RPC）を呼び出し、1回の通信トランザクションでデータベース側で高速にバルク更新を完了させる設計とします。
    - 装備一括操作: `unequip_gear_bulk`, `equip_gear_bulk` RPC
    - スキル一括操作: `unequip_skill_bulk`, `equip_skill_bulk` RPC
    - 装備一括売却: `sell_gear_bulk` RPC

### ② チート対策（RLSおよびサーバー側セキュリティ検証）
*   クライアントからの更新リクエスト（パラメータ改ざん）により、他人の装備品を強奪・操作・売却するチートを完全に防止するため、全ての更新および売却 RPC 内部で、対象アセットの `user_id` がログイン中のユーザーID (`auth.uid()`) と一致しているかを厳密に検証します。
*   専用装備や専用スキルの着脱に関しては、装備対象のキャラクターID (`p_character_id`) のアセットをユーザーが所有しているかをチェックするとともに、マスターデータに定義された専用NPC制限 `exclusive_character_id` と一致しているかをサーバー側で検証し、不正なアライメントや他者専用の装備・スキル装着をデータベースの制約として拒否し、トランザクションをロールバックさせます。

### ③ 装備中のアセット売却および不正売却防止
*   装備中のギアはクライアント側のUI（売却モード）で自動選定対象から除外するとともに、`sell_gear_bulk` RPC 内部で `equipped_character_id IS NOT NULL` （装備中）のレコードが含まれていた場合、処理を中断してエラーを返し、誤売却や不正なアセット消失を防ぎます。
*   売却時には、必ずフロントエンド側で誤操作防止用の「本当に選択した装備品を売却しますか？この操作は取り消せません。」の確認注意ダイアログを表示し、ユーザーの明示的な確認を得てから処理を実行します。

### ① アイテムマスタ構造とレアリティ表現の撤廃

  - **装備強化素材 (EXP)**: `カスタムオイル [小]` (100) / `カスタムオイル [中]` (500) / `カスタムオイル [大]` (2,500)

- **「シノギ」呼称の禁止**: 提案書、コード内コメント、UI上のすべての場所で「シノギ」表記を禁止し、日本語の正式名称 **「クエスト」** で統一します。
- **クエスト**: 消費スタミナ量は `dispatch_courses` マスタ駆動 (初級:10 / 中級:25 / 上級:40)。
- **PvP (アリーナ)**: チケット制廃止。デイリー無料 3回 ＋ キャッシュ追加 2回 ＋ ダイヤ追加 5回 (1日最大10回)。
- **レイド**: チケット制廃止。デイリー無料 3回 ＋ キャッシュ追加 2回 ＋ ダイヤ追加 5回 (1日最大10回)。
- **GvG (抗争)**: 侵攻1回につき 「スタミナ 15」 を消費。終了後に余ったスタミナをクエストへ流すゲームサイクルを維持。

### ③ スタミナ上限回復ガード条件
- エナジードリンク（スタミナ +50）の使用は、**現在のスタミナが 100未満 (0〜99) の場合のみ使用可能**とします。
- 現在のスタミナが 100以上 (100, 110等) の場合は使用不可にし、実質的な最大蓄積量を約 149〜150 に制限します。

### ④ 「覚醒」と「限界突破」の用語 ＆ 重ね合わせ規約
- **キャラクター**: **「覚醒」** (1〜5覚醒)。`覚醒の書` を消費してレベル上限解放およびステータス大幅上昇。
- **スキルカード / 装備品**: **「限界突破」** (+1〜+10)。
  - **同名重ね合わせ**: 基本ルールとして **同名カード / 同名予備装備品** (Lv.1でOK) を消費して限界突破。育てたベース装備 (例: Lv.39) に Lv.1 同名装備を重ねてもベースのレベルは維持されたまま凸数増加。
  - **代用ワイルドカード**: 同名品がない場合に限り、代用素材 (`限界突破の書 [スキル]` / `限界突破の書 [専用スキル]` / `万能カスタムツール [装備]`) を消費して限界突破を実行。
