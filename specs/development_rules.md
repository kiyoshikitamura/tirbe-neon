# 開発ガイドライン ＆ 技術ルール定義書

本作『TRIBE: NEON REIGN』の開発を安全、高品質、かつ迅速に進めるための技術ルール定義書です。前作『code:wirth-dawn』の開発過程で得られた反省・教訓を徹底的に分析し、それらを克服するための強固な開発方針を組み込んでいます。

---

## 1. code:wirth-dawn からの教訓 ＆ 改善設計ルール

### ① データベース：スキーマ無秩序化の防止
- **前作の教訓**: 開発途中の度重なる仕様変更により、不要なテーブルや残骸が残り、コード側との型不整合やデータ不整合を招いていました。
- **改善ルール**: 
  - 本作では `setup_schema.sql` を唯一の正（Single Source of Truth）とし、不要なテーブルや残骸は最初から排除したクリーンな状態で構築します。
  - 新機能（ギルド、レイド、PvP）は初期のスキーマ定義で完全に仕様を固めてからマイグレーションを行い、場当たり的なカラム追加を防止します。

### ② セッション復元 (Resume) の第一級仕様化
- **前作の教訓**: クエスト進行中や戦闘中にリロードが発生した際の状態保持が不完全であり、整合性が崩れるバグが多発していました。
- **改善ルール**:
  - クエスト進行ノード（`currentNodeId`）および戦闘セッション（敵味方個別HP、現在部隊AP、現在の作戦、一時停止状態など）は、**最初からDB（`battle_sessions` テーブル等）へ厳密に永続保存する設計**にします。
  - 画面のリロードが発生しても、何事もなかったかのように直前の状態から復帰できる **「復帰（Resume）ロジック」を最優先のコア機能** として実装します。

### ③ Stripe決済処理の「完全な冪等性」の確保
- **前作の教訓**: Webhookイベント処理時、重複通知に対する防御が緩く、二重処理のリスクを抱えていました。
- **改善ルール**:
  - Stripe決済時は、Webhook受信時に `payment_transactions` テーブルの `stripe_session_id`（ユニーク制約）を用いてトランザクション内でアトミックに競合を検証します。
  - すでにイベントIDが存在する場合は即座に成功を返してスルーする「厳格な冪等性チェック」を強制します。

### ④ スタイリングの無秩序化の排除（Vanilla CSSの徹底）
- **前作の教訓**: Tailwindとad-hocなインラインスタイルが混在し、巨大なファイルとなった結果、表示崩れやスクロール破損の原因になっていました。
- **改善ルール**:
  - **Vanilla CSS を徹底** し、ad-hocなマージンや文字サイズのハードコーディングを全面禁止します。
  - `globals.css` の「ネオンカラーパレット」「フォントトークン」などの変数をCSS変数として一元管理し、これらから呼び出すようにします。
  - 各 UI コンポーネントは独立した CSS ファイルを作成し、コードの肥大化を防ぎます。

### ⑤ 巨大コンポーネントの回避と関心の分離（Context ＆ カスタムフック）
- **追加ルール**: 
  - `page.tsx` 等の単一ファイルに状態や処理を集約することは禁止します。
  - 状態定義とAPI/DB同期ライフサイクルは React Context (`GameContext.tsx`) にて一元管理し、バトル進行などの巨大なドメインロジックは専用カスタムフック (`useBattle.ts`) へ切り出してカプセル化します。
  - 計算処理（装備品ステータスのスケーリングなど）は純粋関数モジュール (`stats_calculator.ts`) として隔離します。

### ⑥ コンポーネント指向CSSの配置ルール
- **追加ルール**:
  - 各 UI コンポーネントファイルは `src/app/components/` に配置します。
  - 対応する CSS ファイルは、コンポーネントと**同一ディレクトリに同名で配置**し、コンポーネントファイル内で直接インポートします。
    - 例：`src/app/components/AuthView.tsx` から `import "./AuthView.css"` を実行。

### ⑦ 全環境共通・モバイル専用縦型レイアウト統一規約 (Single Mobile Architecture)
- **レイアウト崩れ・横幅溢れ・黒帯発生の7大原因完全根絶**:
  - **Next.js ルート DIV (`body > div`) のスタイル強制**: Next.js が自動生成するルート `div` に対し `width: 100% !important; display: flex !important; justify-content: center !important;` を適用し、iOS Safari での左寄せ固着を防止します。
  - **メディアクエリ・PC分岐の全面廃止**: 全 CSS ファイルから `@media` PC分岐および `max-width: 480px` などの固定幅残骸を一掃・全滅させます。
  - **相対配置 (`left: 50%; transform: translateX(-50%)`) の使用禁止**: 要素の右側領域の押し広げ・横ズレを防ぐため、中央配置はすべて純粋な Flexbox / Grid (`width: 100%; display: flex; justify-content: center;`) で行います。
  - **横幅指定の100%統一**: `100vw` の使用を全消去し、`width: 100%` に一元化。iOS Safari でのビューポートオーバーフローを防止します。
  - **`layout.tsx` ＆ `globals.css` での横スライド物理ブロック**: `html, body` に対する `overflow-x: hidden !important;` を常時強制適用します。
  - **Flexbox子要素の `min-width: 0;` 義務化**: 長いテキストや要素による親幅の突き破りを防止します。
- **アセットパス構造の統一**:
  - キャラクターの透過立ち絵画像はすべて **`public/characters/`** ディレクトリ配下に格納し、コード側からは必ず `getCharacterTransparentImg(name)` 経由で取得します。
  - 確定版透過前グリーンバック原画は **`public/raw_assets/<name>_raw.jpg`**（1アセットにつき確定原画1枚のみ）に選別保存します。
- **ロード時間の短縮 (メモリプリロード) ＆ スピナー原則**:
  - コンポーネント初期化時に `useImagePreloader` を呼び出し、立ち絵・背景・UIアセットを事前メモリキャッシュします。
  - 非同期ローディング表示は回転円環スピナーのみを表示し、「Loading...」や「読み込み中...」等のテキストラベル併記は一切禁止します。
- **チート対策・セキュリティ標準 (RLS ＆ サーバーサイドRPC)**:
  - クライアント側（ブラウザ JS）からの不正な直接データ改ざんをシャットアウトするため、Supabase の Row Level Security (RLS) を全テーブルに適用します。
  - Cash, Diamond, Level, Exp, バトル報酬, ギルド献金等の主要トランザクションは、クライアントからの直接 UPDATE を禁止し、必ず PostgreSQL ストアドファンクション（RPC）内で所有権・整合性を検証の上、アトミックに加算・更新します。

## 2. 得意スキルボーナス（AP軽減シナジー）の仕様

- **仕様詳細**:
  - キャラクターが装備しているスキルが得意スキル（ownerIdとキャラクターIDが一致）である場合、自動スキル発動時の**消費APが -1 軽減**されます（※最低消費APは1）。
  - **威力（ダメージ・回復量）の上昇補正や、デバフの持続ターン延長は適用されません。** 等倍（記載スペックのまま）で発動します。
- **実装箇所**:
  - `src/hooks/useBattle.ts` 内のオートスキルAI（手番キャラクターが装備スキルを使用する際のAP消費計算）。
  - `src/app/components/CardBattleView.tsx` 内の `SETUP` (出撃準備画面) でのカード詳細ポップアップ。

## 3. 装備品ステータスのレベル・限界突破スケーリング

- **パラメータ算出式**:
  - レベル（`Level`）および限界突破（`plus_val`）が進行した際の装備ステータス計算式：
    - `ATK / DEF / HP` = `Math.floor(ベース値 * (1 + (Level - 1) * 0.05 + plus_val * 0.10))`
    - `SPD / LUK` = ユーティリティ値 of インフレを防ぐため、常に**フラット（ベース値のまま変化なし）**で計算する。
- **実装箇所**:
  - `src/utils/stats_calculator.ts` の `getCharacterTotalStats` による計算処理。
  - `src/app/components/CharacterTab.tsx` の装備詳細パネル。

## 4. ビジュアル・画像生成コンセプト

- **コンセプト**:
  - サイバー的なド派手な発光カラーを主役に据えるのは避け、**無骨な金属やナイロン等のリアルなストリートギア**を主役に描写する。
  - ライティングとして、**「夜のネオン看板の環境光がエッジに反射しているようなライティング」**（neon rim-light reflections）でディテールに美しく統一感を与える。
- **保留ルール**:
  - まだゲーム上の立ち絵アセット（`user_characters`）が定義されていないキャラクター（レオン、ユウキ、カイト、コハル、サクラなど）の専用武器・専用装備は、**画像アセットの生成をスキップし、モックUI上の表示枠のみ定義する**。

## 5. UI/UX実装・スタイリングの制約

- **Vanilla CSSの徹底**:
  - インラインスタイルや Tailwind 等のad-hocなユーティリティクラスの混用を避け、`src/app/globals.css` に定義された共通変数およびクラスを使用する。
- **ローディング表現**:
  - 非同期処理待ちのローディング表示は、シンプルなスピナーのみ（回転円環のグラフィックなど）を表示する。
  - `Now Loading...` や `読み込み中...` といったローカル文字ラベルの併記・表示は一切禁止。
- **即時レスポンス（押し込み効果）**:
  - ボタン要素には `transform: scale(0.95)` や `active-scale-effect` などのタップ時の押し込みリアクションを必ず付与する。
- **絵文字（Emoji）使用の禁止**:
  - UIのアイコンやラベルに絵文字（📍⚡◆🎁等）を使用することを禁止する。
  - 代わりにSVGアイコン、またはテキストラベル（例: 「拠点」「Cash」「Dia」「AP」）で代替する。
- **スクロールバーのスタイル統一**:
  - スクロールバーにネオンカラー（シアン・マゼンタのグラデーション等）を使用することを禁止する。
  - つや消しメタル調のグレー系（例: `rgba(160, 160, 170, 0.3)`）で統一する。

## 6. ユーザー招待・ギフトコード機能の設計制約

- **テーブル設計と制約**:
  - `users.gift_code` および `user_invitations` テーブルで招待と使用数を一元管理します。
  - 同一の被招待者（新規ユーザー）は1回のみギフトコードを入力可能 (`invitee_id` は UNIQUE 制約)。
- **使用回数の上限**:
  - 各ギフトコードの使用回数は最大10人までに制限。11人目以降が使用しようとすると、例外「このギフトコードは10人使用済です」をスローして初期セットアップを拒否します。
- **報酬の付与**:
  - 招待元のユーザーは、招待ミッション（`m_invite_01`〜`m_invite_10`）を通じてマスタデータを元に1名ずつ報酬を受け取ることができます。
  - 被招待者（入力した新規ユーザー）には、プレゼントBOX (`presents` テーブル) にギフトコード入力報酬（ダイヤ +100）が登録と同時に付与されます。
- **UI/UX のルール**:
  - プロフィール内の「ギフトコードを発行」ボタンを押した際にポップアップでコード表示、コピーボタン、およびLINE招待ボタンを表示します。
  - LINEで招待するボタンは、公式のLINEブランドカラー（`#06C755`）でスタイリングし、適切な文面（自身のギフトコードを含む招待文）を URL スキーム経由で送付可能にします。

## 7. マイページ画面（HomeTab）レイアウト ＆ メニューUI設計規約

### ① ヘッダー（Header.tsx / Header.css）
- **2行構成のモバイルヘッダー**:
  - **Row1**: ユーザー名、所属ギルド名（未所属時は「未所属」バッジ）、レイドアラート（開催時のみ）、総合力
  - **Row2**: Lv.バッジ + 各ステータスの個別枠ボックス（`Cash` / `Dia` / `AP`）
  - 各ステータス枠は `border: 1px solid rgba(255,255,255,0.08)` のボックスで区切り、ラベルテキスト（7px, グレー）＋値テキストで構成する。
- **装飾**: ヘッダー上部に `margin-top: 8px` のスペースを確保。上下に金のグラデーションライン（`border-image`）を配置。CSSグラデーション背景のみで構成し背景画像は使用しない。

### ② 拠点情報オーバーレイ（ビジュアルエリア上部）
- ビジュアルエリア**内部**の最上部に `position: absolute` で配置。
- 背景は上から下への透過ダークグラデーション（`rgba(0,0,0,0.75)` → `transparent`）。
- テキストラベル「拠点」+ 拠点名 + 「｜」+ 「支配: ギルド名」を1行に集約。右端に「拠点移動」ボタン。

### ③ サブメニューアイコン（左右分散・ラベル付き）
- 左側: ミッション、プレゼント（ゲームプレイ系） / 右側: お知らせ、設定（情報・設定系）
- 拠点オーバーレイの下（`top: 42px`）に配置。インラインSVG + テキストラベル。バッジカウント表示あり。

### ④ ビジュアルエリアのCSS
- `height: 50vh; overflow: hidden;` で固定。内部要素は `position: absolute` で配置。
- **リーダーキャラクター立ち絵と拠点背景ビジュアル（アバター一時オミット中）**:
  - マイページ中央にはお気に入りNPC立ち絵が表示され、背景には現在滞在している拠点に対応する背景画像（`bgUrl`）が表示されます（ちびアバター表示と固定背景は一時オミットされています）。
  - ※ただし、将来アバター機能が有効化された際は、アバター用固定背景の上にレイヤードアバターを重ね合わせ描画する仕様へ切り替えが可能です。

### ⑤ 丸型漢字メニューボタン（連合 / 喧嘩 / 制圧）
- ビジュアルエリアの**外側**（兄弟要素）に配置し、`margin-top: -48px` のネガティブマージンでビジュアルエリアに重ねる。
- `position: relative; z-index: 15;` で前面に表示。中央の喧嘩ボタンを最大サイズ（`96px`）、左右は `80px`。
- ボタン画像は `public/menu/menu_allies.png`, `menu_fight.png`, `menu_conquest.png`（画像内に漢字描画済み）。
- HTML上のテキスト重ねは排除する。

### ⑥ チャットウィジェット
- 丸ボタンの直下に配置（間に不要なスペースを入れない）。
- チャットログは `height: 108px; min-height: 108px; max-height: 108px;` で常に6行分の固定サイズを確保し、サイズを可変させない。
- ヘッダー部クリックで開閉可能（閉じ時はヘッダー1行のみ表示）。
- スクロールバーはつや消しメタル調グレー（ネオンカラー禁止）。

### ⑦ フッター
- `マイページ`, `ガチャ`, `ギルド`, `キャラクター`, `メニュー` の5項目。
- SVGアイコン + テキストラベル構成。「メニュー」タップで各機能へのリンク一覧画面（MenuTab）に遷移する。

### ⑧ UIアセットのクロマキー透過処理ワークフロー
- ゲームUI用のボタンやバッジ、小アイコン画像を新規に生成・追加する際は、文字・背景台座・ファンタジー要素を排した `solid chroma key green background #00FF00`（完全単色緑背景）で生成し、Node.jsスクリプト（`scratch/chromakey_icon_generic.js`）を通じて自動的に周囲の緑を透過（アルファ値0）した透過PNG（`public/ui/<name>.png`）に加工してから適用します。原画は `public/raw_assets/<name>_raw.jpg` に管理保存します。

## 8. ランキングシステム ＆ 新設画面設計規約

### ① ランキング画面の構造と遷移導線
- **新設画面 (`RankingTab`)**: 総合力、ギルド総合力、PvP、GvG、レイドの5つのカテゴリをサブタブで切り替え、さらに「デイリー」「シーズン」をトグルで表示切り替えできる一元化画面として構成する。
- **ホーム画面サブアイコン**: 左側サブメニュー（ミッション・プレゼントの横）に、星または王冠をモチーフとした透過SVGアイコン（絵文字禁止）とラベルテキスト「ランキング」を配置する。
- **メニュー一覧画面**: `MenuTab` の一覧に「ランキング」ボタン（シルバーカラーベース、`menu-tab-item--silver` クラス）を配置する。

### ② 総合力計算と同期のタイミング
- **総合力計算**: パーティデッキの3名（未設定時は所持キャラ上位3名）の `hp + atk + def + spd + luk` の合算値とする。
- **同期処理**: ログイン時、およびキャラクターのレベルアップ、覚醒、装備変更などのステータス更新時に、`syncUserPower` を経由して `user_power_rankings` テーブルに `current_power` を即時 upsert する。

### ③ スタイリング規約 (Matte Outlaw UI への準拠)
- **スチール行**: リスト項目にはつや消しスチール調の行スタイル（`steel-row` クラス、ダークメタルグラデーション背景と微細な境界線エッジ）を適用する。
- **順位 badge**: 1〜3位にはそれぞれ金・銀・銅の鈍い金属光沢グラデーション反射を適用し、ネオン反射を演出する。
- **スクロールバーの統一**: つや消しメタル調のグレー系（`rgba(160, 160, 170, 0.3)`）で統一し、シアンやマゼンタなどのネオンカラースクロールバーは使用禁止とする。

## 9. アバターシステム（ロード最適化・着せ替え・メイキング）設計規約 (一時オミット中)
> [!IMPORTANT]
> アバターシステム関連のUI/UX設計規約（メイキング画面・着せ替え画面・マイページアバター表示）は、現在一時オミットされ、メニューおよび登録画面からの導線は無効化されています。
> ただし、将来アバター機能が有効化された際にすぐ動作するよう、バックグラウンドのデータ構造・同期ロジック・画像プリロード等は実装が生かされています。

### ① アバター初期アセットの仕様
- **表情・髪型のバリエーション**: 男女それぞれに各4種類（合計8種類）の初期アセットを定義する。
- **初期服装**: ベーシック（黒タンクトップ＋ショートパンツ、シューズなし）の1種類に限定する。
- **背景エフェクト**: アバターの後ろに重ねるエフェクトを最大2枠装着可能とする。

### ② ロード時間短縮 ＆ UX保護対策
- **WebPフォーマットの強制**: すべてのアバターパーツ画像は、透過処理対応でかつ軽量な `WebP` 形式（解像度: 最大512x512程度）として用意・保存する。
- **メモリへのプリロード（プリフェッチ）**: ログイン時の `syncBootstrapData` 実行時に、現在装着中のパーツ画像およびデフォルトアセット画像をバックグラウンドでメモリにプリロードする。
- **全パーツ読込完了の同期**: レンダラーコンポーネント内で全装着パーツ画像のロード完了（`onLoad`）を検知するまでプレースホルダー（影絵やスピナー）を表示し、パーツが欠けた状態のちらつきを防ぐ。

### ③ アバターセットアップ（キャラクターメイキング）※自動処理
- 新規ユーザー登録時 (`SetupView`) は、アバターメイキングUIは表示せず、デフォルトのアバター値（男、初期ツンツン髪、初期通常表情）を自動登録する仕様とする。

### ④ アバター着せ替え画面 (AvatarTab) ※非表示

## 11. レイドシステム（ボス・報酬マスタ・ボーナス）設計規約

### ① ボスエネミーのマスターデータ化
- レイドボスのステータス（HP、ATK, DEF, SPD, LUK、表示名、レベル）およびスキル配列は、`raid_boss_master` テーブルにてマスタ定義を行う。
- バトル開始時（`startCardBattle`）には、このマスタからボスのステータスとスキル配列を取得してエネミー部隊を動的に構築し、ハードコーディングを排除する。

### ② レイド報酬のマスター定義と自動配布
- レイド報酬は、`raid_rewards_master` にて一括管理し、撃破報酬（`DEFEAT`）、累積ダメージ報酬（`DAMAGE_ACCUM`）、個人ランキング報酬（`RANK_PERSONAL`）、ギルドランキング報酬（`RANK_GUILD`）を定義する。
- **自動配布**: 累積報酬はしきい値を超えた戦闘終了時に、撃破報酬はボスHPが0になった瞬間に、それぞれ自動で `presents`（プレゼントBOX）へ配布し、`user_raid_claimed_rewards` に受け取り履歴を記録する。

### ③ 4拠点ランダム出現
- レイドボスの出現・リセット（時間切れ、または討伐成功による復活）時には、GvGの4つの主要拠点（ネオンタワー、ディープドック、ジャンクバザール、キタクラゲート）の中からランダムに1拠点を選択してボスを出現（`base_id` を更新）させる。

### ④ エリア支配ダメージボーナス (+20%)
- プレイヤーの所属ギルドが、ボスが出現している拠点を制圧（GvGの支配ポイントが1位）している場合、レイドバトルでの与ダメージに +20% の補正を適用する。戦闘ログに「【支配ボーナス発動】」を表示する。

### ⑤ 画面遷移と正式名称の統一
- タイトル表記は正式名称の「レイド」に統一する。
- 画面内の簡易ランキング表示をオミットし、「ランキングで確認」ボタンを設置して、ランキング画面の「レイド」カテゴリ（`RankingTab` の `raid`）へ直接遷移させる。

## 12. PvP（PvP）システム開発・同期ルール

### ① ゼロレイテンシ同期（SWRパターン）の徹底
- PvP対戦相手の表示においては、遷移時に都度全画面ローディングを挟んで操作をブロックすることは禁止する。
- 前回の取得マッチング候補データをステート（`pvpOpponents`）に保持し、画面遷移時はそれを **0秒で即座に表示** させた上で、バックグラウンドにて `fetchPvpOpponents` を非同期実行して最新化し、レスポンス返却後にリストを更新する。

### ② 画像アセットのバックグラウンドプリロード
- 対戦相手候補のデータ取得が成功した時点で、各候補の1番目の防衛キャラクター（リーダー）の立ち絵画像などを `Image` オブジェクトを用いてバックグラウンドで事前ロードする。
- これにより、ユーザーが「対戦」ボタンを押して戦闘画面へ切り替わった際の画像読み込みによる「ちらつき」やロード待機時間を極限まで排除する。

### ③ ローディングインジケータにおける文字ラベル排除
- PvP画面を含め、非同期のローディングインジケータ（`opponentsLoading` 等）の描画時にはシンプルな回転スピナーのみを表示する。
- `Now Loading...` や `読み込み中...` などのローカル文字列の併記・表示は開発ガイドラインの制約に基づき一切禁止する。

### ④ 敵ステータス計算と作戦AIの適用
- 敵キャラクターの防衛ステータス（HP, ATK, DEF, SPD, LUK）の計算には、限界突破レベルや装備品の数値を反映した `getCharacterTotalStats` を適用する。
- 敵側のギルドメイン・サブアライメントとキャラクター属性が一致する場合、アライメント防衛ボーナス（+20% / +10%）をパラメータへ乗算した上でバトルを開始する。
- 戦闘中の敵ターン実行時（`executeEnemyTurn`）は、対戦相手の防衛デッキに登録された `tactic` （作戦設定）に従って、挑発キャラクターの優先狙撃、HP低下メンバーへの回復スキル選択、シールド展開などを実行するAIロジックを正確に走らせる。

## 13. ガチャ ＆ キャラクター入手システム開発・設計ルール

### ① 完全データベース駆動（マスタ定義）
- ガチャバナーごとの名称、消費コスト（キャッシュ／ダイヤ／有償ダイヤ）、説明文はすべて `gacha_masters` テーブルより取得します。
- 排出アイテムおよびそのウェイト（重み）は、`gacha_items_master` から取得したウェイト比率を用いて乱数による重み付け抽選を行います。
- クライアント側やAPIサーバー側にガチャの排出確率やコストの静的データをハードコーディングすることは禁止します。

### ② 新規キャラクター獲得時の初期セットアップ自動化
- チュートリアルガチャや通常のキャラクターガチャでキャラクターを獲得した際、それがプレイヤーにとって「最初の1人（所持キャラクター数が0名）」である場合、以下の初期設定を一括して自動実行します：
  - お気に入りリーダー（`users.favorite_character_id`）にそのキャラクターを設定。
  - 初期スキルカードを `user_skills` にインサートし、そのキャラクターに装備。
  - 初期装備品一式（武器・頭・体・足・アクセサリー）を `user_equipments` にインサートし、そのキャラクターに自動装備。
- プレイヤーが初期メンバーを全く持たない状態でゲームが開始されるため、この自動セットアップは戦闘可能なキャラクターを即時に用意するために必須の仕様となります。

### ③ 重複獲得時の覚醒および素材自動変換
- ガチャで排出されたキャラクターがすでに組織に加入（所持）している場合：
  - キャラクターの覚醒段階 `awakening_level` を +1 加算（最大★5まで）して `user_characters` を更新します。
  - すでに覚醒段階が最大（★5）の状態で重複した場合は、覚醒用共通素材である「抗争の掟（`LAW_OF_STRIFE`）」を `user_items` に +1 加算し、自動変換結果を結果画面に表示します。

### ④ 毎日無料10連ガチャ ＆ スペシャルガチャの制御
- キャラ・スキル・装備の各カテゴリで毎日1回10連ガチャが無料（JST 0:00リセット）で利用できます。
- 常設スペシャルガチャ（R以上確定、200Pt天井あり）およびノーマルガチャ（毎日10連無料対応）が提供され、所持通貨不足時は自動的にショップ（闇取引）画面へ遷移します。

## 16. 装備・スキルの一括操作、売却およびチート・ロード時間対策

### ① ロード時間短縮（通信バルク化）
*   所持装備・スキル数が増大するゲームデザインにおいて、1スロットずつ個別に Supabase API で更新を行うと、全身装着時（装備7スロット、スキル6スロット）に膨大な通信オーバーヘッドが発生し、ロード時間の遅延およびネットワークエラーの原因になります。
*   これを防止するため、一括解除および一括装備は必ず Supabase のストアドファンクション（RPC）を呼び出し、1回の通信トランザクションでデータベース側で高速にバルク更新を完了させる設計とします。
    - 装備一括操作: `unequip_gear_bulk`, `equip_gear_bulk` RPC
    - スキル一括操作: `unequip_skill_bulk`, `equip_skill_bulk` RPC
    - 装備一括売却: `sell_gear_bulk` RPC

### ② チート対策（RLSおよびサーバー側セキュリティ検証）
*   クライアントからの更新リクエスト（パラメータ改ざん）により、他人の装備品を強奪・操作・売却するチートを完全に防止するため、全ての更新および売却 RPC 内部で、対象アセットの `user_id` がログイン中のユーザーID (`auth.uid()`) と一致しているかを厳密に検証します。
*   専用装備や専用スキルの着脱に関しては、装備対象のキャラクターID (`p_character_id`) のアセットをユーザーが所有しているかをチェックするとともに、マスターデータに定義された専用NPC制限 `exclusive_character_id` と一致しているかをサーバー側で検証し、不正なアライメントや他者専用の装備・スキル装着をデータベースの制約として拒否し、トランザクションをロールバックさせます。

### ③ 装備中のアセット売却および不正売却防止
*   装備中のギアはクライアント側のUI（売却モード）で自動選定対象から除外するとともに、`sell_gear_bulk` RPC 内部で `equipped_character_id IS NOT NULL` （装備中）のレコードが含まれていた場合、処理を中断してエラーを返し、誤売却や不正なアセット消失を防ぎます。
*   売却時には、必ずフロントエンド側で誤操作防止用の「本当に選択した装備品を売却しますか？この操作は取り消せません。」の確認注意ダイアログを表示し、ユーザーの明示的な確認を得てから処理を実行します。

## 17. ガチャ天井システム ＆ 友達（Tomodachi）・助っ人参戦ルール

### ① ガチャ天井システムとマイレージ交換
- **マイレージ加算**: ガチャ1回ごとに `user_gacha_pity_points` へ 1Pt が累積加算されます（10連で +10Pt）。
- **プログレス表示 ＆ 交換所モーダル**: ガチャ画面（`GachaTab`）上にプログレスバーを表示し、「天井Pt確定交換所」モーダルから対象キャラ・最高レア装備（名称、ステータス、必要Pt）が一覧で確認・直接交換できます。
- **友達ポイントの排除**: 友達ポイント（FP）システムは実装せず、ポイント付与処理を行いません。

### ② 友達 (Tomodachi) システムと上限管理
- **名称統一**: 全てのドキュメントおよびUIで「フレンド」の呼称を禁止し、**「友達」**で統一します。
- **上限30人**: 友達の登録上限は **最大 30人** とし、30人に達した場合は新規申請・許可を制限します。
- **自己紹介モーダル連動申請**: ランキング・ギルド・チャット等でプレイヤーアイコンをタップした際、構成員プロフィール（自己紹介モーダル）から「＋ 友達申請」ボタンでどこからでも申請可能です。

### ③ 助っ人バトル参戦計算 (`useBattle.ts`)
- 出撃準備画面（`SETUP`）で助っ人キャラクターを1名選択して出撃可能。
- 自部隊5名 ＋ 助っ人1名の **最大6人部隊** でバトルに参戦し、助っ人のLevel、装備ステータス、得意スキル（AP-1軽減）判定が `useBattle.ts` のターンAIおよびバトル計算にそのまま組み込まれます。

## 18. 全60キャラクターアセット生成 ＆ レアリティ判定運用ルール
1. **全60キャラクター同等高粒度設計**:
   - 特定のレアリティ限定ではなく、全60キャラクターすべてにおいて、ストーリー背景・外見特徴・衣装・持ち物・表情・専用英語生成プロンプトを最高精度かつ同一の粒度で定義します。
2. **全画像生成後のクオリティ順レアリティ振分**:
   - キャラクターのレアリティ割り振り（SSR 10名 / SR 20名 / R 20名 / N 10名）は事前決定せず、60名の画像生成がすべて完了した後に、グラフィックの完成度・出来栄え順に後から割り振りを確定します。
3. **放置少女スタイルの完全全身立ち絵統一**:
   - 既存UI（マイページ全画面立ち絵キャンバスや構成員詳細表示）との親和性と美観を追求するため、全ての立ち絵プロンプトは頭の先から靴先までを含む「完全な全身立ち絵 (`full body portrait, full standing figure from head to toe`)」に統一します。
4. **緑色衣類・要素被色時のクロマキー背景柔軟変更**:
   - 自動アルファ透過処理（`scratch/chromakey.js`）の精度を維持するため、基本は単色グリーンバック (`solid chroma key green background`) としますが、キャラクターの衣装・髪・背景小物等に緑色が多く含まれる場合は、誤透過を防ぐためマゼンダ (`solid chroma key magenta background`) やブルー (`solid chroma key blue background`) 等、透過しやすい最適な単色バックを柔軟にプロンプト指定して生成します。
