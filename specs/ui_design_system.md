# UIデザインシステム

最終更新: 2026-08-09

## 1. 目的と優先順位

本書は、TRIBE NEONのバトル中画面を除く全UIに適用する、デザイン・レイアウト・状態・表示性能・クライアント信頼境界の正本である。

共通UIについて他文書と記述が異なる場合は本書を優先する。画面固有の機能、表示項目、ゲームルールは各機能仕様を優先する。作品全体の画風・構図・生成条件・Asset QAは`art_bible.md`を正本とし、`visual_concept.md`は旧来の詳細資料として参照する。

本書の対象は以下とする。

- PvPハブ
- クエスト・派遣ハブ
- ギルド
- GvGハブ
- レイドハブ
- ミッション
- ガチャ
- コミュニティ（チャット／BBS）
- フレンド
- ショップ
- マイバック
- プレゼントボックス
- お知らせ
- 設定
- ログインボーナス
- 拠点移動
- 共通ヘッダー、下部ナビゲーション、モーダル、通知、ローディング

マイページとキャラクターページにも共通規則を適用するが、本番マスタ・本番画像投入後に最終調整する。バトル中の盤面、攻撃再生、スキル演出、リザルト演出は別フェーズで設計する。

## 3. デザイン原則

### 3.1 世界観

- 現代東京の夜、歓楽街、ストリート、裏社会を基調とする。
- マットブラック、鉄、くすんだ金、深い赤を基本とする。
- シアン、マゼンタ、紫は、UI自体の電子発光ではなく、夜の看板光が金属面へ反射した環境色として扱う。
- SF、ホログラム、細い電子パネル、全面的なネオングローを避ける。
- 強い光と動きは、最高レア、重要報酬、勝敗、開催中イベントへ限定する。

### 3.2 情報階層

各画面で最初に読ませる内容を次の3点に絞る。

1. 現在の目的
2. 現在の結果・状態
3. 次の行動

補助説明、履歴、詳細値はタブ、展開領域、詳細モーダルへ移す。バッジは「今対応する理由」がある場合だけ表示する。

### 3.3 片手操作と可読性

- 主要操作のタップ領域は最小44px、標準48pxとする。
- 本文は原則12px未満にしない。補助ラベルのみ10〜11pxを許可する。
- 色だけで状態を示さず、文言、アイコン、数値を併用する。
- 一画面のPrimary操作は原則1つとする。
- 固定UIで本文やSafari操作領域を隠さない。

## 4. デザイントークン

### 4.1 カラー

| トークン | 値 | 用途 |
| --- | --- | --- |
| `--ui-bg-root` | `#070A10` | アプリ最背面 |
| `--ui-bg-surface` | `#0E141F` | 通常画面・カード |
| `--ui-bg-raised` | `#151D2A` | モーダル・選択項目 |
| `--ui-border` | `#34404E` | 通常境界 |
| `--ui-text-primary` | `#F4F6F8` | 見出し・重要情報 |
| `--ui-text-secondary` | `#A5AFBC` | 説明・日時 |
| `--ui-text-disabled` | `#697482` | 無効・未解放 |
| `--ui-accent` | `#27D7E6` | 選択中・通常主操作 |
| `--ui-value` | `#D6AD3E` | 価値・戦力・報酬・SSR |
| `--ui-combat` | `#D94B46` | 戦闘・レイド・危険状態 |
| `--ui-limited` | `#C83D7D` | 期間限定・特別商品 |
| `--ui-gvg` | `#7958B3` | GvG特殊状態 |
| `--ui-success` | `#3AB66F` | 完了・成功 |
| `--ui-warning` | `#D89432` | 注意・期限 |

シアンを全カードの枠へ使用しない。ゴールドは価値、赤は戦闘・危険、マゼンタは限定、緑は完了という意味を維持する。通常状態で複数色を競合させない。

### 4.2 文字

| 用途 | サイズ | 規則 |
| --- | --- | --- |
| 画面タイトル | 18〜20px | 太字、短い日本語 |
| 重要数値 | 20〜28px | 折返し禁止、桁幅確保 |
| セクション見出し | 14〜16px | 太字 |
| 本文 | 12〜14px | 十分な行間 |
| ボタン | 12〜14px | 太字 |
| 補助情報 | 10〜11px | 長文禁止 |
| バッジ | 9〜10px | 件数または短語 |

太い漢字の決め表現は、勝敗、撃破、抗争開始、報酬獲得などへ限定する。英字は装飾ラベルに使用できるが、意味を英字だけへ依存させない。

### 4.3 余白・形状

- 基本余白単位は4pxとし、4／8／12／16／24pxを使用する。
- 通常カードの角丸は6〜8px、モーダルは10〜12pxとする。
- 通常境界は1pxとし、常時太い発光枠を使用しない。
- カード内余白は標準12px、密な一覧は8pxとする。

## 5. 共通画面構造

通常画面は次の順序に統一する。

1. 共通ヘッダー
2. 画面タイトル／開催状態
3. 画面の主題となるHero領域
4. Primary操作
5. タブまたはフィルター
6. 一覧・詳細
7. 共通下部ナビゲーション

### 5.1 レイアウト規則

- 単一モバイル構造、最大幅430pxを維持する。
- `100vw`ではなく`width: 100%`を使用する。
- スクロール担当は一画面に一つだけ設ける。
- Flex／Grid子要素には必要に応じて`min-width: 0`を設定する。
- 上部安全領域はアプリシェルで一度だけ確保し、個別画面で重ねない。
- 下部ナビゲーションと`safe-area-inset-bottom`を共通シェルで管理する。
- 画面固有の固定ボタンを下部ナビゲーションへ重ねない。
- 画像領域はロード前からアスペクト比と寸法を確保する。

## 6. 画面テンプレート

| テンプレート | 対象 | 基本構造 |
| --- | --- | --- |
| 戦闘・イベントハブ | PvP、クエスト、GvG、レイド | 開催状態、対象、自分の状態、主操作、編成／報酬／履歴 |
| コミュニティハブ | ギルド、チャット／BBS、フレンド | 所属概要、最新の動き、主操作、メンバー／投稿、管理 |
| 報酬・タスク | ミッション、プレゼント、ログインボーナス | 受取可能数、カテゴリ、一覧、一括受取、結果 |
| 収集・経済 | ガチャ、ショップ、マイバック | Hero、所持通貨、一覧、詳細、確認、獲得結果 |
| 補助パネル | お知らせ、設定、拠点移動 | タイトル、カテゴリ、項目、保存／確定、結果 |

PvP、クエスト、GvG、レイドのハブまでは本書の対象とする。バトル開始後の画面は共通バトル仕様として後工程で実装する。

## 7. 共通コンポーネント

### 7.1 ボタン

- `Primary`: 画面の主操作。原則1つ。高さ48px。
- `Secondary`: 編成、詳細、交換所など。暗いマット面と通常境界。
- `Ghost`: 戻る、閉じる、絞り込みなど。
- `Danger`: 脱退、削除、解除。確認ダイアログ内で強調する。

全ボタンに通常、押下、選択中、無効、処理中、完了を実装する。処理中は文言を維持して小型スピナーを添え、二重送信を禁止する。無効化はUXであり、権限制御の根拠にはしない。

### 7.2 面と一覧

- `HeroPanel`: 戦況、ボス、ガチャ対象など画面の主題。
- `Card`: 操作可能なまとまり。
- `ListRow`: 履歴、投稿、アイテムなど大量表示。
- `Badge`: 未読、未受取、対応必要件数。常設説明の代替として使用しない。
- `RarityFrame`: 装備、スキル、報酬で共用する。

### 7.3 モーダル

モーダルは詳細、操作、確認の3種類に限定する。

- 中央表示を基本とする。
- 長い内容だけ内部スクロールを許可する。
- モーダルの上へ別モーダルを重ねない。
- 成功結果は同じモーダル内で切り替える。
- 背景タップで閉じる可否を目的別に明示する。
- iPhone Safariで`position: fixed`を多重使用しない。
- ブラウザ標準の`alert`、`confirm`を使用しない。

### 7.4 横方向のカテゴリ・拠点選択

- 横幅に収まらない同階層の選択肢は、画面固有の横スクロールを作らず共通`SubTabNav`を使用する。
- PCとモバイルの双方に前後矢印を表示し、移動できない側だけ無効化する。
- モバイルの直接操作は横方向へ限定し、縦方向の画面スクロールへ選択列を追従させない。
- 選択中項目は表示領域内へ移動し、末尾の項目が見切れたまま操作不能にならないようにする。
- クエスト拠点、ランキング部門など、同じ階層・同じ操作目的には同一部品を適用する。

## 8. 共通状態

各画面は次の状態を持つ。

- 初回読み込み
- キャッシュ表示可能
- 空
- 未解放
- 開催前
- 開催中
- 終了／完了
- 通信失敗
- 処理中
- 成功
- 権限不足
- 所持不足
- 上限到達

空状態は理由と次の行動を示す。通信失敗は再試行を提供する。未解放は必要条件を示す。状態を色だけで表現しない。

## 9. ロード・画像表示・キャッシュ

### 9.1 一括表示の原則

画像をHTMLへ個別に出し、読み込み完了順に段階表示してはならない。

表示しようとする画面を一つのロード単位とし、その画面の初期表示に含まれる以下がすべて準備できてからスピナーを解除する。

- 必須データ
- 背景
- キャラクター、敵、ボス等の主画像
- 初期表示されるアイテム、装備、スキル、報酬アイコン
- UI画像
- 代替画像

画面ごとにアセットマニフェストを定義し、`Promise.all`相当の共通ローダーで完了を管理する。画像失敗時は、事前ロード対象に含めた代替画像へ解決する。必須画像と代替画像の双方が失敗した場合は、部分表示せずエラー状態と再試行を表示する。

「一括表示」は全アプリの全画像を起動時に読む意味ではない。現在表示する画面単位で必要な画像一式を準備する。次画面の先読みはアイドル時に行えるが、先読み途中の画像を画面へ露出しない。

### 9.2 スピナー

- 未キャッシュ画面は中央の共通スピナーを表示する。
- `Loading...`、`読み込み中...`等の文字を併記しない。
- 次画面の準備中は、可能なら現在画面を維持し、その上で遷移中スピナーを表示する。
- 画像の段階表示、スケルトンから実画像への順次置換は採用しない。
- 保存、受取、購入など局所的な通信は、対象ボタンまたは対象カードに小型スピナーを表示する。
- 初期画面を成立させる複数の並列処理は、すべて完了するまで全体スピナーを維持する。

### 9.3 キャッシュ

- ハッシュ付き静的アセットは長期ブラウザキャッシュを利用する。
- 画面アセットマニフェストはビルドまたはコンテンツバージョンで失効させる。
- 共通マスタはバージョン付きでキャッシュし、バージョン変更時に一括更新する。
- ユーザー情報は用途別にキャッシュし、更新成功後は影響するキーだけ再検証する。
- 同じ取得要求は重複実行せず、一つの進行中Promiseを共有する。
- 一覧、チャット、BBS、履歴はページネーションまたは仮想化し、全履歴を初回取得しない。
- キャッシュ済みデータと画面画像一式が揃っている場合は、スピナーを省略して即時表示できる。
- キャッシュ表示後のバックグラウンド更新で構造を突然差し替えず、新着バッジまたは明示的な更新として反映する。

### 9.4 性能目標

| 対象 | 目標 |
| --- | --- |
| キャッシュ済み画面遷移 | 0.5秒以内 |
| 未キャッシュ画面の操作可能化 | p75で2.5秒以内、p95で4秒以内 |
| モーダル・タブ切替 | 0.3秒以内 |
| 主要API応答 | p75で1秒以内、p95で2秒以内 |
| 画面画像一式の準備 | p75で2.5秒以内、p95で4秒以内 |
| バトル開始準備 | p75で3秒以内、p95で5秒以内 |

画像一括表示のために性能目標を緩和しない。画像圧縮、適正解像度、キャッシュ、アセット数削減で達成する。

## 10. クライアント信頼境界とチート対策

ブラウザ、JavaScript、DOM、クライアントキャッシュ、表示中のマスタ値はすべて改ざん可能な非信頼領域として扱う。

### 10.1 サーバーを正本とする値

- Cash、ダイヤ、AP、各種メダル
- レベル、経験値、戦力、ステータス
- 所持、装備、スキル、編成
- ガチャ抽選、購入、交換、報酬
- ミッション進捗、受取、ログインボーナス
- PvP、GvG、レイド、クエストの開始条件、結果、ランキング、クールダウン
- ギルド権限、加入、脱退、寄付、役職
- 開催時刻、期限、利用回数、在庫

クライアントは入力候補と表示を担当し、結果値を決定しない。

### 10.2 更新規則

- ゲーム性に関わる更新は、認証済みRPC、サーバー処理、またはEdge Functionを通す。
- RPC内で`auth.uid()`、所有権、残高、期限、回数、状態遷移、参照マスタを再検証する。
- 残高減算、報酬付与、履歴記録は一つのトランザクションで行う。
- クライアントから重要テーブルへの直接INSERT／UPDATE／DELETEをRLSで拒否する。
- クライアントが送る価格、報酬量、戦力、ダメージ、勝敗、経過時間を信用しない。
- 二重送信・再送へ備えて、重要処理に冪等性キーまたは一意制約を設ける。
- サーバー時刻を使用し、端末時刻を期限・開催判定へ使用しない。
- 異常頻度、整合性違反、失敗した権限操作を監査可能な形で記録する。
- Service Roleキー、決済秘密鍵、署名秘密鍵をクライアントへ含めない。

UIのボタン無効化、非表示、クライアント側バリデーションは操作補助であり、チート対策には数えない。

### 10.3 バトル

バトル開始、編成確定、乱数、行動順、ダメージ、報酬、勝敗はサーバー側で確定する。クライアントは確定済みの再生データを描画する。バトル中UIの実装時に、再生データ形式、署名または改ざん検知、再送、途中復帰、速度変更の信頼境界を別途確定する。

## 11. モーション

- 押下: 80〜120ms
- タブ切替: 150〜180ms
- モーダル: 180〜240ms
- 受取・成功: 300〜500ms
- 高レア・大勝利: 最大1.2〜1.8秒
- 常時アニメーションは低頻度・低負荷とする。
- スクロール中は装飾アニメーションを抑制する。
- `prefers-reduced-motion`と低負荷設定を用意する。
- 絵文字をUIアイコンとして使用しない。

### UI-2: コミュニティ

### UI-3: 報酬・経済

- ミッション

### UI-4: 補助

- お知らせ

### DATA: マスタデータ作成

UIで確定した表示契約に合わせ、画面文言、商品、報酬、開催、レアリティ等のマスタを作成する。クライアント表示用マスタをサーバー判定の根拠として信用しない。

### ASSET: 不足画像生成

確定したアスペクト比、表示密度、レアリティ階層に合わせて不足画像を生成・圧縮し、画面アセットマニフェストへ登録する。

### BATTLE: バトル中画面

他UI、マスタ、主要画像が揃った後、バトル盤面、準備、再生、スキル、決定イベント、リザルトを実装する。サーバー確定結果を再生する構造とし、バトル固有のUI・演出仕様を別文書へ確定する。

### POLISH: UI最終調整

本番マスタ、本番背景、本番キャラクター、装備、スキル、報酬画像を投入し、全画面の配色、コントラスト、余白、文字量、光量、演出強度を調整する。マイページとキャラクターページもここで再監査する。

### TUTORIAL: 初回体験

完成した本編UIとバトルを前提に、タイトル、認証、登録、チュートリアル、通常プレイへの接続を実装する。

## 13. 完了条件

- 共通部品を画面固有CSSで複製していない。
- 主目的、現在状態、次の行動が一目で分かる。
- 初回、空、未解放、処理中、失敗、成功を確認できる。
- 画面画像が段階表示されず、一式準備後に表示される。
- キャッシュ済み再訪で不要な再取得・再デコードを行わない。
- iPhone Safariの上下安全領域を侵害しない。
- ゲーム性に関わる値と更新をクライアントだけで決定していない。
- 型チェック、ビルド、E2E、実機確認を通過している。
