# UI段階実装計画

最終更新: 2026-08-10

進捗: UI-0A（Stage 0）完了。UI-0Bの共通基盤を適用し、UI-1（クエスト、PvP、GvG、レイド、ランキング）を実機確認用fixture込みで確認中。監査結果と移行台帳は[ui_stage0_audit.md](ui_stage0_audit.md)を参照する。

UI-1の確認データはQAアカウントに限定し、PvP対戦相手、防衛デッキ、ギルド所属、公式GvGマッチ、開催中レイド、各ランキングのMY STATUSを同一fixtureで準備する。fixtureはリロードでは実行せず、初回migration適用時または設定画面の「テストデータを投入」を明示的に操作した時だけ再適用する。バトル開始後の画面はBATTLE Stageまで無効表示とする。

## 1. 目的

本書は、TRIBE: NEON REIGNのバトル中画面を除くUIを、画面ごとの都度修正ではなく、共通基盤と画面テンプレート群の単位で完成させる実装計画の正本である。

共通デザイン、ロード、キャッシュ、信頼境界の仕様は`ui_design_system.md`、画面の監査状態は`ui_release_audit_backlog.md`を参照する。本書は実行順、成果物、完了条件、実機確認地点を管理する。

## 2. 進行ルール

- 個別画面の局所調整から着手しない。
- 共通部品で解決できる問題を画面固有CSSで修正しない。
- 各Stageの途中状態は`main`へpushしない。
- Stage内は複数コミットに分けてよいが、品質ゲート通過後にまとめてpushする。
- Vercelでの実機確認は、同じテンプレートを使う画面群が揃った段階で行う。
- マスタ未完成部分は共通fixtureで正常、空、未解放、処理中、失敗等を再現する。
- ホームとキャラクターページは毎Stageで回帰確認するが、本番データ・本番画像による最終調整は後工程で行う。
- PvP、クエスト、GvG、レイドのハブと、それらを横断するランキングは先に整えるが、バトル開始後の画面はASSET工程後の独立Stageで実装する。
- 画面の表示制御やボタン無効化をセキュリティ対策として扱わない。

## 5. UI-0B: 共通基盤

### 5.1 デザイン基盤

- デザイントークン
- `PageShell`
- `PageHeader`
- `HeroPanel`
- Primary／Secondary／Ghost／Dangerボタン
- Tabs／Filter
- Card／ListRow
- Badge
- ResourceDisplay
- RarityFrame
- Modal／ConfirmDialog

### 5.2 状態基盤

- Spinner
- EmptyState
- ErrorState
- LockedState
- PermissionState
- ProcessingState
- SuccessState
- Countdown／開催状態

### 5.3 ロード・キャッシュ基盤

- 画面単位のアセットマニフェスト
- 必須データと画像の並列ロード
- 全画像完了後の一括表示
- 事前ロード済み代替画像
- 必須画像失敗時のエラーと再試行
- 同一要求の進行中Promise共有
- ハッシュ付き静的画像の長期HTTPキャッシュ
- バージョン付きマスタキャッシュ
- ユーザーデータの短期キャッシュ
- 更新成功後の対象キーだけ再検証
- 導線表示後のアイドルプリフェッチ

初回に全アプリの全画像を読み込まない。現在表示する画面の初期表示画像一式を一つの単位として準備し、途中状態を画面へ露出しない。

### 5.4 セキュア操作基盤

- クライアントから重要テーブルへの直接更新を禁止する。
- ゲーム性に関わる更新をRPCまたはEdge Functionへ統一する。
- 所有権、残高、期限、回数、状態遷移をサーバー側で再検証する。
- 二重送信防止と処理中表示を共通化する。
- 重要処理へ冪等性キーまたは一意制約を設ける。
- サーバーエラーを共通UI状態へ変換する。
- 更新後は影響範囲のキャッシュだけ再検証する。

### 5.5 完了条件

- 新規画面で個別のボタン、カード、モーダル、スピナーを作る必要がない。
- 画面画像が読み込み順に段階表示されない。
- 上下安全領域を共通シェルで一度だけ管理できる。
- 主要操作が共通の処理中、成功、失敗状態を持つ。
- UI-1の5画面へ同じ基盤を適用できる。

UI-0B単独では実機承認を求めず、UI-1の実画面へ適用した状態で確認する。

## 11. UI後工程

### DATA: マスタデータ作成

UIで確定した表示契約に合わせ、文言、商品、報酬、開催、レアリティ、取得元等のマスタを作成する。

### ASSET: 不足画像生成

確定したアスペクト比と表示密度に合わせ、背景、キャラクター、敵、装備、スキル、報酬、UI画像を生成・圧縮し、画面アセットマニフェストへ登録する。

### BATTLE: バトル中画面

他UI、マスタ、主要画像が揃った後に実装する。

- バトル準備
- 盤面
- 通常攻撃
- 通常スキル
- 固有スキル
- 決定イベント
- リザルト
- スキップ、倍速、途中復帰
- サーバー確定結果の再生
- 再生データの改ざん対策

### POLISH: UI最終調整

本番マスタと本番画像を投入し、全画面の配色、光量、余白、文字量、コントラスト、演出強度を調整する。ホームとキャラクターページもここで最終監査する。

### TUTORIAL: 初回体験

完成した本編UIとバトルを前提に、タイトル、認証、登録、チュートリアル、通常プレイへの接続を実装する。

### RELEASE: 総合回帰

UI以外の機能、データ、運用、セキュリティ、性能を含めてリリース判定する。

## 12. 進捗更新方法

- Stage開始時に`ui_release_audit_backlog.md`を「監査中」または「実装中」へ更新する。
- Stage内の完了項目を本書へ逐次追加せず、監査台帳で管理する。
- 方針や順序を変更した場合は、本書の更新日、工程表、対象、完了条件を同じコミットで更新する。
- 各Stageのpush後に、コミットID、CI結果、実機確認URL、確認対象タブをユーザーへ提示する。
